    PostgreSQLの対応環境と接続選択

    検証したリリース、必要バージョンの宣言、reader / writerの選択と更新時の確認。

    対応環境と検証範囲

    PHP 8.4 / 8.5（64bit）、Laravel 12 / 13、PostgreSQL 18 / 19を対象とします。PostgreSQL 19の確認済みリリースは19rc1です。正式版での検証は未完了です。

    区分確認した構成範囲
    通常依存PHP 8.4 / 8.5 × Laravel 12 / 13 × PostgreSQL 18.6 / 19rc18構成。各構成で482テストと配布パッケージの導入・実DB実行を確認
    最低依存PHP 8.4 + Laravel 12 + PostgreSQL 18.6、PHP 8.5 + Laravel 13 + PostgreSQL 19rc12構成。同じテストと配布確認を実行
    異なるバージョンの接続独立したPostgreSQL 18.6 / 19rc1のDBreader / writerの選択、transaction、sticky、reconnect / purgeを5ケースで確認

    2026-10-20の実装検証に基づく範囲です。19側の5構成ではバージョンが異なる接続の試験も実行しました。単一の環境での成功を、すべてのPHP・Laravel・DBの組合せや利用アプリの動作保証とは扱いません。

    クエリに必要なバージョンを宣言する

    queries.<ID>.postgres_min_version は整数の18（既定）または19です。コンパイルはDBに接続せず、実行直前にLaravelが選んだPDOのバージョンを確認します。必要なバージョンを満たさない場合は登録SQLを送らず TW_CONNECTION になります。

    php
    'queries' => [
    'items.get_or_create' => [
        'path' => 'items/get_or_create.sql',
        'kind' => 'write_returning',
        'postgres_min_version' => 19,
        'parameters' => [
            'id' => ['type' => 'int64'],
            'value' => ['type' => 'text'],
        ],
    ],
],

    SQLの書き方はPostgreSQL 19のget-or-createを参照してください。19専用SQLを18向けに自動変換する機能はありません。宣言を変更したら生成物とASTキャッシュも更新します。

    reader / writerのバージョンが異なる場合

    接続名ごとに一括判定せず、実際の実行先を検査します。以下は通常のreadを中心とした接続選択の契約です。write / RETURNINGは常にwriterを使用します。

    状態検査する接続19専用クエリ
    transaction外、writer18 / reader19reader19実行可能。未使用のwriterを開かない
    transaction外、writer19 / reader18reader18登録SQLを送らず拒否
    既存transaction内 / lockingwriterwriter18なら拒否、writer19なら実行可能
    write後のsticky読取writerwriterのバージョンで判定
    Laravelのreconnect / purge後再生成されたPDO以前の検証結果を流用せず再判定

    writer19 / reader18では、transaction内で成功した19専用検索が、rollback後にreaderへ戻ると拒否される場合があります。接続選択はLaravelの状態に従います。

    タイムアウト・plan advice・each / eachAsには追加の接続条件があります。別reader PDOを使う場合は接続構成と実行オプションを確認してください。

    この確認は、独立した2台の隔離DBで接続の選択を調べたものです。異なるメジャーバージョン間の物理レプリケーションやデータ複製の整合性を検証したものではありません。

    RC版と正式版を区別する

    server_version_num=190000 だけでは19rc1と19.0を区別できません。環境の確認では SHOW server_version の実リリース表記も記録してください。実行時の最低バージョン判定と、そのリリースを検証済みとする判断は別です。

    19正式版での対応確認には、通常8構成・最低依存2構成に加え、配布パッケージの導入、19専用SQL、reader / writerの選択、plan adviceの導入時・未導入時の再検証が必要です。現時点の19rc1の結果を正式版の実績として表示しません。

    今回の更新とアプリ側の確認

    2026-10-20の更新では、接続検証・transaction / savepoint・例外処理・診断を共通の実行処理へ整理し、実行API・DAO生成・PHPStanの操作契約を共通化しました。公開API、SQL文法、クエリ種別、既存の生成PHP・manifest形式を維持しています。内部クラスをアプリから直接呼び出す必要はありません。

    入力値を含む例外の扱い、DTO変換失敗時のrollback、cursor解放、observer失敗が結果を変えないことを回帰テストで確認しています。利用アプリの認可・テナント条件や外部ログの設定は、引き続きアプリ側で管理してください。

    更新時はホストアプリの composer.lock を更新してレビューし、デプロイ手順に沿ってSQL・設定・生成物を検査します。最新の変更概要は変更履歴を参照してください。
