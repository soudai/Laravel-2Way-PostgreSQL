    エラーとトラブルシューティング

    全エラーコードと、設定・入力・接続・生成物を確認する手順。

    最初に確認すること

    まず php artisan twoway:lint で登録・文法を確認します。入力スキーマ、SQL ID、kind、PDO/サーバー要件を順に照合し、DBの調査は合成データと隔離環境で行います。

    php
    use Hft\TwoWaySql\Exception\SqlException;

try {
    $rows = $queries->select('users.search', $parameters);
} catch (SqlException $e) {
    // errorCode、sqlId、spanの行/列で原因を分類する。
    // 実入力やbindingsを診断ログへ追加しない。
    throw $e;
}

    SqlExceptionは errorCode、sqlId、span、parameterPath を公開します。DB実行失敗のSqlExecutionExceptionには sqlState があります。元のDB例外本文をpreviousへ保存しない設計です。

    エラーコード一覧

    code 主な原因 確認・対応
    TW_SYNTAX テンプレート構造・式が不正 end、命令行、条件の型、1文制約を確認
    TW_UNSUPPORTED 未対応の構文・実行形態 別reader PDOでのscope/streaming、未ロードadvice module等を確認
    TW_SAMPLE バインド後のサンプル不備 scalar/listの形、リテラル、cast位置を確認
    TW_PARAMETER_MISSING 必須キー欠落 nullableでもキーを渡す。nested arrayの階層を確認
    TW_PARAMETER_EXTRA 未宣言キー 余剰キー、dotを含む入力キー、patch fieldを除く
    TW_PARAMETER_TYPE 型・宣言・オプション不一致 int/bool/日時、NULL許容、未知設定、Codecを確認
    TW_EMPTY_LIST 空リストの選択展開 空を業務としてどう扱うか、SQL構造と入力で明示
    TW_EMPTY_SET 空の更新SET/patch 更新対象がある場合だけ呼び出す
    TW_LIMIT byte数・件数・深さ等の上限 入力/SQLを縮小し、必要なら予算を明示調整
    TW_TEMPLATE_PATH ID・path・rootが不正 登録ID、存在する相対.sql、権限、symlinkを確認
    TW_QUERY_KIND SQL/API/kindの不一致 writeとreturning、readとlocking等の契約を合わせる
    TW_CONNECTION DB設定・最低版・テスト接続検査 native prepares、PDO例外、UTF8、strings=on、version、markerを確認
    TW_TRANSACTION_REQUIRED lockingをtransaction外で実行 同じLaravel connectionのtransaction内へ移す
    TW_CARDINALITY 厳密件数違反 one=1行、oneOrNull=0/1行、scalar=1行1列を確認
    TW_EXECUTION DB実行やcallbackの失敗 sqlState・SQL IDで分類し、隔離環境で調査
    TW_MAPPING DTO・結果型の変換不備 alias、重複列、NULL、constructor、SqlType/converterを確認
    TW_SORT 未登録ソート・不正定義 text入力とsortsのキー、column/direction/nullsを確認
    TW_AFFECTED_ROWS 期待更新件数と不一致 ID/tenant/version条件と実際の対象を照合
    TW_BATCH バッチ途中の失敗 failedIndex、completedIndexes、causeCode、sqlStateを確認
    TW_GENERATION DAO/生成/列metadataの不一致 schema、signature、path、手編集、manifestを確認
    TW_COMPATIBILITY 文法混在・version宣言不足 queryのgrammar、19専用SQLのpostgres_min_versionを確認

    よくある症状

    Artisanコマンドが見つからない

    パッケージがホストアプリへインストールされ、自動検出が有効かを確認します。Laravelのpackage:discoverとautoloadを再生成してください。パッケージの開発リポジトリ自体にartisanはありません。

    nullableにしたのにパラメータ欠落になる

    nullableはNULL値を許可する指定です。キー省略の許可ではありません。['name'=>null] のように明示し、dot pathならネストした配列を渡します。

    timestamp文字列が拒否される

    組込みtimestampは YYYY-MM-DD HH:MM:SS.ffffff を要求します。例えば 2026-01-01 12:30:00.000000。timestamptzは文字列でなくDateTimeInterfaceです。

    SQLを更新したのに生成物checkが失敗する

    SQL hashも生成契約に含まれます。開発環境で該当するgenerate / generate-schemaをwriteし、差分をレビューしてからcheckを再実行します。生成ファイルの手編集は上書きしません。

    通常の検索は動くがtimeoutやeachが失敗する

    read/write分離で別reader PDOが選ばれていないか確認します。transaction scopeをLaravelが管理できるnamed connectionへ切り替えてください。

    PG19のSQLをPG18で動かしたい

    自動fallbackは提供しません。18向けSQLを別途用意し、必要な契約を明示してください。19の宣言を外すだけでは対応になりません。

    GitHub上でHTMLがソース表示になる

    GitHubのファイル画面はHTMLをWebページとして実行しません。リポジトリを取得して docs/html/index.html をブラウザで開くか、このフォルダを静的Webサーバーで配信してください。外部CDNやビルドは不要です。

    調査用のコマンド

    bash
    php artisan twoway:lint
php artisan twoway:check tests/sql/cases.json --json
php artisan twoway:generate --check
php artisan twoway:generate-schema users.search --params=SearchParams --dto=UserRow --check

    ケース・生成物を利用している対象について実行します。実DBのmetadataや計画を調べる場合は inspect / explain と 隔離DBの設定 を使用してください。
